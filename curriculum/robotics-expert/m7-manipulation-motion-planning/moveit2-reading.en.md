# Reading MoveIt 2: move_group, the planning scene, and execution

Just as M6 read Nav2 as an assembly diagram of its parts, this lesson reads MoveIt 2 as the
assembly diagram of this module. The goal is to see where IK (M2), collision checking and OMPL
(lesson 5), time parameterization (lesson 3), and trajectory tracking (lesson 2) each slot in.

## Concepts

### move_group and the robot model

At the center is the **move_group** node. You send goals through the C++ `MoveGroupInterface`,
Python `moveit_py`, or the RViz MotionPlanning plugin, and move_group takes care of planning and
execution. The robot model comes from two files.

- **URDF:** links, joints, limits, and collision geometry (the M8 tf2 and URDF lesson).
- **SRDF:** planning groups (`manipulator`, `gripper`, say), end effectors, named poses (`home`),
  and link pairs that can never collide.

These settings, along with `kinematics.yaml` (an IK plugin such as KDL), `joint_limits.yaml`, and
`ompl_planning.yaml`, usually live in a `*_moveit_config` package generated by the MoveIt Setup
Assistant.

### The planning scene

The **planning scene** is "the world right now." It holds the joint state (`/joint_states`),
collision objects (tables, boxes), attached objects being held, and the depth sensor octomap, and
it is the reference for collision checking. An object being held must be attached to the gripper
for collision checking during transport to be correct (lesson 4).

### The planning pipeline and execution

1. A goal (joint values, a pose, a named pose) arrives; a pose goal becomes a joint goal through
   the IK plugin.
2. The planning pipeline calls a planner (OMPL RRTConnect by default, Pilz, CHOMP, STOMP), and
   request and response adapters add start state checking, path simplification, and **time
   parameterization**.
3. The result is a `trajectory_msgs/JointTrajectory` (joint names, and per point the position,
   velocity, acceleration, and `time_from_start`).
4. The trajectory execution manager sends it as a `FollowJointTrajectory` action to
   **ros2_control**'s `joint_trajectory_controller`, which interpolates between points and
   commands the hardware interface.

For real-time teleoperation use **MoveIt Servo** (the Jacobian-based velocity control of lesson 1,
with slowdown near singularities); for multi-stage pick-and-place, use the **MoveIt Task
Constructor (MTC)**.

### Reading the code

The core flow of the First C++ Project tutorial (simplified, for reading):

```cpp
using moveit::planning_interface::MoveGroupInterface;
auto move_group = MoveGroupInterface(node, "manipulator");  // planning group name from the SRDF
move_group.setPoseTarget(target_pose);                        // becomes a joint goal through IK
MoveGroupInterface::Plan plan;
if (move_group.plan(plan)) {     // planning pipeline: OMPL + simplification + time parameterization
  move_group.execute(plan);      // FollowJointTrajectory -> ros2_control
}
```

## Key formulas

The minimum time satisfying the joint limits when parameterizing the interval
$[\theta_a, \theta_b]$ with a quintic polynomial (lesson 3):

$$T = \max_i \max\!\left(\frac{15}{8}\frac{|\Delta_i|}{v_{i,max}},\ \sqrt{\frac{10}{\sqrt{3}}\frac{|\Delta_i|}{a_{i,max}}}\right)$$

## Example

Attach timing to four three-joint waypoints to build the point list of a `JointTrajectory`
structure, and check the typical conditions a controller rejects (limit violations, a
non-monotonic `time_from_start`).

```python
import numpy as np

# joint waypoints from the planner (no timing) and the limits corresponding to joint_limits.yaml
waypoints = np.array([[0.0, -0.5, 1.0], [0.6, -0.2, 0.7], [1.2, 0.3, 0.2], [1.5, 0.4, -0.3]])
VMAX = np.array([1.0, 1.0, 1.5])  # rad/s
AMAX = np.array([2.0, 2.0, 3.0])  # rad/s^2
KV, KA = 15 / 8, 10 / np.sqrt(3)  # max velocity and acceleration coefficients of a quintic (lesson 3)


def quintic(tau):
    s = 10 * tau**3 - 15 * tau**4 + 6 * tau**5
    sd = 30 * tau**2 - 60 * tau**3 + 30 * tau**4
    sdd = 60 * tau - 180 * tau**2 + 120 * tau**3
    return s, sd, sdd


# 1) time parameterization: per segment, the minimum time keeping every joint within limits
#    (a simple version that stops at each waypoint)
points, t0 = [], 0.0  # (positions, velocities, accelerations, time_from_start)
for qa, qb in zip(waypoints[:-1], waypoints[1:]):
    d = np.abs(qb - qa)
    T = max(np.max(KV * d / VMAX), np.max(np.sqrt(KA * d / AMAX)))
    for tau in np.linspace(0, 1, 11)[:-1]:
        s, sd, sdd = quintic(tau)
        points.append(
            (qa + s * (qb - qa), sd / T * (qb - qa), sdd / T**2 * (qb - qa), t0 + tau * T)
        )
    t0 += T
points.append((waypoints[-1], np.zeros(3), np.zeros(3), t0))
print(f"{len(waypoints)} waypoints -> {len(points)} trajectory points, {t0:.2f} s total")

# 2) checks on the controller side: limit violations and monotonically increasing time
vel = np.array([p[1] for p in points])
acc = np.array([p[2] for p in points])
times = np.array([p[3] for p in points])
print("max |v|/VMAX:", (np.abs(vel).max(axis=0) / VMAX).round(3))
print("max |a|/AMAX:", (np.abs(acc).max(axis=0) / AMAX).round(3))
print("time_from_start monotonically increasing:", bool(np.all(np.diff(times) > 0)))
for k in [0, 5, 10, len(points) - 1]:
    q, v, _, t = points[k]
    print(f"  t={t:5.2f}s  positions={q.round(3) + 0.0}  velocities={v.round(3) + 0.0}")
```

The result is a 31-point trajectory of 3.61 s in total, with the busiest joint of each segment
reaching its acceleration limit (ratio 0.998). At a waypoint such as $t = 1.32$ s the velocity is
zero. This simple version, stopping at every waypoint, is safe but slow. MoveIt 2's time-optimal
parameterization (TOTG) treats the whole path as one and passes through waypoints without
stopping.

**Exercise:** (1) Halve `VMAX` and see how the total time and the limit ratios change.
(2) Implement cubic Hermite interpolation that sets the velocity at intermediate points to the
mean of the adjacent segments so the trajectory does not stop at waypoints, and compare the total
time. (3) Follow the Quickstart in RViz of the MoveIt 2 Tutorials (if you have it installed) and
check the `time_from_start` of the planning result the same way as in this example.
